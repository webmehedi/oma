# Phase playbook: 05-qa

Read by the orchestrator. Not read by agents.

## Preconditions

- Gate `04-build` is `approved`.
- No blocking `open_questions` for `user`.

## The loop — bounded at 3 iterations

This is the phase that separates "runs" from "looks finished." The verification
loop: QA judges → dev agents repair → QA re-judges. Two structural rules make
it converge instead of thrash:

- **QA never fixes; fixers never judge.** Enforced by the agents' definitions;
  your job is never asking a dev agent to "verify your own fix is good" — the
  verification is the next QA run.
- **Three iterations, then stop.** An unbounded repair loop is the fastest way
  to spend a fortune producing nothing. After 3, the user decides.

### Iteration (repeat up to 3 times)

**1. Dispatch oma-qa**, foreground, with this preamble plus:

```
You run in the project root (the directory containing .oma/). All `.oma/...`
paths in your role file are relative to it, and ${CLAUDE_PLUGIN_ROOT} is the
installed OMA plugin directory.

Iteration: {state.qa.loop_iteration + 1} of 3.
Report template: ${CLAUDE_PLUGIN_ROOT}/templates/qa-report.md
Write your report to .oma/05-qa/reports/run-{N}.md.
{iteration 1: "Also author test-plan.md and the critical-path e2e tests."}
{iteration ≥ 2: "Fix tasks T-x..T-y were filed last run — verify each, and
check for regressions around the touched areas."}
You may write .oma/04-build/tasks.json directly — you run alone this phase.
```

**2. Reconcile**: read QA's handoff and report. Update `state.qa`
(`last_run`, the five pipeline verdicts, `open_failures`, `loop_iteration`).
Surface `contract_changes` immediately if any.

**3. Branch:**

- **All green** (pipeline passes, no open fix tasks) → go to Gate.
- **Failures filed and iteration < 3** → dispatch the fix round: group open
  `fix` tasks by owner; dispatch **oma-frontend** and/or **oma-backend**
  (same-message parallel if both have work), stage `fix`, each with its task
  slice and the QA report path. On return, reconcile handoffs into tasks.json
  (`tasks_completed` → `done`), then loop back to step 1.
- **Iteration == 3 and still red** → STOP. Set phase `blocked`. Report to the
  user: the failure list with evidence, what was tried across iterations
  (from the run reports), and the options — accept specific failures as known
  issues (`/oma:gate approve` with notes moves them to `wontfix`), keep
  iterating (`/oma:run` re-enters with the counter reset — their explicit
  choice, not yours), or dig in manually.

## Gate presentation

Set `awaiting_gate`. Show:

1. The verdict table from the final run report — real commands, real exit codes.
2. Requirements coverage: `must` REQs verified / untested (untested rows named
   honestly — this is what the user is accepting).
3. Anything QA flagged as `warn` or suspicious (flaky tests, weakened
   assertions caught).
4. If approving over known failures: list exactly which, and note they become
   `wontfix` with the gate notes as the reason.
5. `/oma:gate approve` / `/oma:gate reject "why"`.

## Brownfield

- **`extend`** — verify the new feature against its REQs, and separately confirm
  the baseline stages that were green in `.oma/00-archaeology/baseline.md` are
  *still* green. A regression in untouched code is the failure mode that matters
  most when adding to someone's existing system.
- **`refactor`** — QA's whole job is proving nothing changed. The existing suite
  passing unchanged is the contract. Any test that had to be modified is a
  finding, not a fix, and gets reported with the diff.
- **`audit`** — QA runs the pipeline and reports, and files findings as tasks
  nobody is dispatched to fix. Never present an audit's task list as work in
  progress; it is a backlog handed to the user.

**Never mark a pre-existing failure as an OMA regression.** Compare against the
baseline before filing anything: if a stage was already red when the
archaeologist arrived, say so in the report and leave it out of the loop count.
